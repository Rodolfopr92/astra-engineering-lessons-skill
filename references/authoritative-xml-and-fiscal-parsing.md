# Authoritative XML & Fiscal NF-e Parsing

## 1. Safe XML Parsing Without Parser Vulnerabilities

Parsing XML payloads received from external users introduces multiple high-severity attack vectors:
1. **XML External Entity (XXE) Attacks**: Exploiting XML external entities to read arbitrary host files.
2. **Billion Laughs & Quadratic Blowup (DTD Entity Expansion)**: Exponential entity expansion exhausting server memory.
3. **Deep Recursion Attacks**: Nesting XML tags thousands of levels deep to exhaust thread call stacks.
4. **Control Character Injection**: Embedding null bytes or terminal escape sequences to corrupt downstream logs or databases.

### Safe Parser Implementation (`roxmltree`)
Astra uses `roxmltree` (read-only, zero-copy):
- `roxmltree` does not resolve external entities.
- Any document declaring a `<!DOCTYPE ...>` block is immediately rejected by `roxmltree` with `Error::DtdDetected`.
- Astra adds two additional layers of defense:
  1. **ASCII Control Character Pre-check**: Rejecting bytes `< 0x20` (except `\t`, `\n`, `\r`) before parsing.
  2. **Max Depth Recursion Guard**: Recursively validating that no element exceeds a nesting depth of 32.

```rust
pub fn parse_safe_xml(xml: &str) -> Result<roxmltree::Document<'_>, StructuredParseError> {
    if xml.len() > MAX_XML_SIZE_BYTES {
        return Err(StructuredParseError::SecurityViolation("file exceeds 20 MB limit".into()));
    }
    validate_xml_characters(xml)?;
    let doc = roxmltree::Document::parse(xml)
        .map_err(|e| StructuredParseError::MalformedXml(e.to_string()))?;
    check_node_depth(doc.root_element(), 1)?;
    Ok(doc)
}
```

## 2. Fixed-Point Fiscal Arithmetic (`rust_decimal::Decimal`)

### The Floating-Point Fallacy
In standard software, engineers frequently model currency with `f64`. In fiscal engineering, this is **strictly forbidden**:
```text
0.10 + 0.20 = 0.30000000000000004
```
A one-cent or fractional drift causes invoice rejection, fiscal accounting audits, and broken sum validations.

### The Solution
All quantities, unit prices, discounts, freight charges, and tax bases use `rust_decimal::Decimal`:
- Native fixed-point representation.
- Serde serialization configured with `serde-with-str` to preserve exact string numbers (e.g. `"1850.00"`).
- Direct implementation of `SurrealValue` for zero-conversion database persistence.

## 3. Brazilian NF-e 44-Digit Access Key & Modulo 11 Check Digit

The Brazilian Electronic Invoice (NF-e) access key is a 44-character numeric string structured as follows:
- Digits 01–02: UF (State Code)
- Digits 03–06: AAMM (Year and Month of emission)
- Digits 07–20: CNPJ of the issuer
- Digits 21–22: Model (`55` for NF-e, `65` for NFC-e)
- Digits 23–25: Series
- Digits 26–34: Invoice Number
- Digits 35–35: Emission Type (`1` for Normal, etc.)
- Digits 36–43: Random Code (cNF)
- Digit 44: Modulo 11 Check Digit (cDV)

### Modulo 11 Algorithm
Weights `2..9` cycle from right to left across the first 43 digits:
```rust
let mut sum = 0u32;
let mut weight = 2u32;

for &digit in digits[..43].iter().rev() {
    sum += digit * weight;
    weight += 1;
    if weight > 9 {
        weight = 2;
    }
}

let remainder = sum % 11;
let expected_cd = if remainder < 2 { 0 } else { 11 - remainder };
```
Any mismatch between `expected_cd` and `digits[43]` is an authoritative verification failure (`InvalidAccessKey`).

## 4. Totals Consistency & Tolerance Policy

In real Brazilian fiscal operations, rounding individual items (`vProd = qCom * vUnCom`) can diverge slightly from the declared total `vProd` or `vNF` due to 2-decimal vs. 4-decimal rounding rules.

Astra enforces a strict **R$ 0.02 tolerance policy**:
- `|sum(items.v_prod) - totals.v_prod| == 0`: Exact match, zero warnings.
- `0 < discrepancy <= 0.02`: Document is valid; an informational rounding warning is logged.
- `discrepancy > 0.02`: Document is flagged with an authoritative discrepancy warning for manual review.

## 5. SEFAZ Protocol Capture (`<nfeProc>`)

An NF-e XML can exist in two forms:
1. **Raw `<NFe>`**: The invoice payload generated by the ERP. It does not prove that the tax authority (SEFAZ) approved the invoice.
2. **Distribution `<nfeProc>`**: Contains the `<NFe>` payload wrapped alongside the SEFAZ authorization protocol (`<protNFe>`).

Capturing protocol fields at parse time is critical for fiscal ordering:
- `nProt`: SEFAZ Protocol Number (e.g. `135260000000001`).
- `cStat`: SEFAZ Status Code (`100` = Authorized).
- `xMotivo`: Status explanation (e.g. `Autorizado o uso da NF-e`).
- `dhRecbto`: Official SEFAZ receipt timestamp.

## 6. Contextual Invoice Direction Derivation

NF-e XML is symmetric: it describes an exchange between `<emit>` and `<dest>`. The XML itself never contains a label saying "inbound" or "outbound". Direction is contextual:
- If `active_tenant_cnpj == emit.CNPJ`: **Outbound** (invoice issued by the tenant to a client).
- If `active_tenant_cnpj == dest.CNPJ` (or `dest.CPF`): **Inbound** (invoice received by the tenant from a vendor).
- If tenant is unconfigured or neither matches: **Unknown**.

By recording this at parse time, downstream analytics never need to re-parse raw XML to determine revenue vs. expense.

## 7. Deduplication vs. Duplicate Conflict Detection

When an invoice arrives:
1. **Idempotent Replay**: If the access key is already in the database and the associated `artifact_id` matches, the existing record is returned without re-inserting items or mutating balances.
2. **Duplicate Conflict**: If the access key already exists under a *different* `artifact_id`, Astra detects an identity collision, aborts with `NFE_DUPLICATE_CONFLICT`, and routes the payload to the dead-letter queue. This prevents unauthorized overwrites or double-counting of invoices.
